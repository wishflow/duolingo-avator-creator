# 03.2 Codex 本地语义标注

## 1. 背景与结论

03.1 已经把运行时生成链路改为 semantic catalog 驱动：前端提交可用选项，Worker 让模型输出目标特征，再由 Worker 匹配合法 `state/value`。这个方向可以避免模型直接猜 Rive 数字值，但 catalog 本身仍需要更可靠的视觉语义标签。

Codex 本地标注通道用于生成和复核视觉语义，不直接接入用户 Generate，不替代 03.1 的运行时设计。

关键结论：

- Codex 负责看图、识别语义、按固定 JSONL 输出标注结果。
- 脚本负责机械任务：枚举 option、渲染三栏对比图、生成任务包、校验 JSONL、生成分批报告、合并审核通过的结果。
- 标注 `tags` 改为开放标签，不再被少量 `allowedTags` 限制。
- `attributes` 用于记录多维视觉特征，第一版只存在于 JSONL 和报告，不进入正式 catalog，不参与 Worker 匹配。
- 全量标注先落在 `.cache/`，默认 `reviewStatus=pending`；只有人工改为 `approved` 的结果才允许合并到 `assets/avatar_semantic_catalog.json`。

## 2. 适用边界

| 项目 | Codex 本地标注 | Actions / Cloudflare 视觉模型 |
| --- | --- | --- |
| 运行位置 | Codespaces 当前工作区 | GitHub Actions |
| 调用方式 | 人工让 Codex 按任务包分批看图 | workflow_dispatch 手动触发 |
| 模型职责 | 识别三栏对比图，输出开放 JSONL | 通过 Cloudflare REST 视觉模型输出结构化结果 |
| 结果落地 | 本地 JSONL 和 Markdown 报告，经审核后合并 | Draft PR 或 artifact |
| 优点 | 易复核、可解释、能快速人工纠偏 | 可重复、批量化、无需交互 |
| 风险 | 交互式，批量耗时；开放标签需要人工审核 | 受模型和 API 质量影响；成本和密钥管理更重 |

不应把 Codex 设计成“自动枚举和持久化所有结果”的唯一执行引擎。确定性操作必须放在项目脚本里；Codex 只做视觉判断和 JSONL 输出。

## 3. 整体流程

```mermaid
flowchart TD
  C[avatar_builder_config.json] --> E[枚举 feature options]
  E --> B[渲染 baseline PNG]
  E --> O[渲染 option PNG]
  B --> D[生成 diff PNG]
  O --> D
  D --> T[三栏对比图 baseline | option | diff]
  T --> P[按 batch 生成任务 JSON]
  P --> L[Codex 写入该 batch 独立 labels JSONL]
  L --> R[生成该 batch 独立 Markdown 报告]
  R --> I[生成总索引报告]
  I --> H[人工审核 reviewStatus]
  H --> M[只合并 approved 到 catalog]
```

三栏对比图是默认输入，原因是单张 option 图容易漏掉细节变化，尤其是表情、皱纹、耳饰、鼻环、眼镜边框等小元素。

```
+----------------+----------------+----------------+
| baseline       | option         | diff           |
| 默认头像截图   | 当前选项截图   | 像素差异高亮   |
+----------------+----------------+----------------+
```

## 4. Codespaces 浏览器准备

渲染 Rive 头像需要真实浏览器运行 Rive/WASM、应用 state、从 `riveCanvas` 导出 PNG。Codex 可以识别图片，但图片仍必须先由浏览器渲染得到。

推荐准备命令：

```bash
npx playwright install --with-deps chromium
```

脚本查找浏览器的顺序：

| 顺序 | 来源 | 说明 |
| --- | --- | --- |
| 1 | `CHROME_EXEC` | 用户显式指定浏览器路径，优先级最高 |
| 2 | 系统命令 | `google-chrome`、`google-chrome-stable`、`chromium`、`chromium-browser` |
| 3 | Playwright Chromium 缓存 | 从 `~/.cache/ms-playwright/` 中查找 `chrome-linux/chrome`、`chrome-linux64/chrome` 等可执行文件 |

如果三者都找不到，任务生成应失败，并提示先执行 Playwright 安装命令或设置 `CHROME_EXEC`。

## 5. 脚本接口

这些命令由 `scripts/semantic_codex.py` 和 npm scripts 提供。

| 命令 | 作用 |
| --- | --- |
| `npm run semantic:codex:tasks -- --sample FacialHair:1` | 生成单个 option 的任务包和三栏对比图 |
| `npm run semantic:codex:tasks -- --smoke` | 生成跨组 5 个样本任务 |
| `npm run semantic:codex:tasks -- --all-features --batch-size 10` | 生成全部 feature option 的分批任务 |
| `npm run semantic:codex:merge -- --input .cache/avatar-semantic/codex/labels/features-001.jsonl --check-only` | 校验某一批 JSONL；默认要求 `reviewStatus=approved` 才可合并 |
| `npm run semantic:codex:report` | 读取任务包和各批 labels，生成分批报告和总索引 |
| `npm run semantic:codex:compare -- --codex ... --cloudflare ...` | 对比 Codex 与 Cloudflare 标注差异 |

缓存目录：

| 路径 | 说明 |
| --- | --- |
| `.cache/avatar-semantic/codex/tasks/` | 每批任务 JSON |
| `.cache/avatar-semantic/codex/images/` | 三栏对比图 |
| `.cache/avatar-semantic/codex/labels/` | 每批独立 JSONL |
| `.cache/avatar-semantic/codex/reports/` | 每批独立报告和总索引 |
| `.cache/avatar-semantic/codex/merge-report.json` | 最近一次合并校验报告 |
| `.cache/avatar-semantic/codex/compare-report.md` | 与 Cloudflare / Actions 结果的对比摘要 |

`.cache/` 已忽略入库，只有审核后合并的 `assets/avatar_semantic_catalog.json` 和必要复核文档进入提交。

## 6. JSONL 输出格式

Codex 标注结果采用 JSONL，每行对应一个 option。开放标签 schema 固定为 `schemaVersion=2`。

```json
{
  "schemaVersion": 2,
  "optionId": "MainHair:48",
  "group": "main_hair",
  "tags": ["short_hair", "rounded_hair", "side_coverage", "neat_style"],
  "attributes": {
    "length": "short",
    "shape": ["rounded_top"],
    "coverage": ["top", "sides"],
    "style": ["neat"]
  },
  "confidence": 0.82,
  "needsReview": false,
  "reviewStatus": "pending",
  "evidence": "The option adds a short rounded hairstyle with side coverage.",
  "labelSource": "codex_manual",
  "imagePath": ".cache/avatar-semantic/codex/images/MainHair_48.compare.png"
}
```

字段规则：

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| `schemaVersion` | 是 | 固定为 `2` |
| `optionId` | 是 | 必须存在于当前 `avatar_builder_config.json` 枚举结果 |
| `group` | 是 | 必须等于该 option 的 semantic group |
| `tags` | 是 | 开放视觉标签；模型可自由生成，不再限制在受控词表内 |
| `attributes` | 是 | 多维视觉特征对象；只用于 JSONL 和报告，不进入 Worker 匹配 |
| `confidence` | 是 | `0..1`，低于阈值时合并为 `needsReview: true` |
| `needsReview` | 是 | 模型主观不确定、图像差异过小、标签冲突时为 `true` |
| `reviewStatus` | 是 | `pending`、`approved`、`rejected`；模型默认写 `pending` |
| `evidence` | 是 | 简短视觉证据，说明为什么选择这些标签 |
| `labelSource` | 是 | 固定为 `codex_manual` |
| `imagePath` | 是 | 指向本次识别使用的三栏对比图 |

合并脚本必须拒绝以下结果：

- JSON 解析失败或缺少必填字段。
- `schemaVersion` 不是 `2`。
- `optionId` 不存在、重复或不在当前任务包中。
- `group` 与 catalog 枚举结果不一致。
- `tags` 不是非空字符串数组。
- `attributes` 不是对象。
- `confidence` 不是 `0..1` 数字。
- `reviewStatus` 不是 `pending`、`approved`、`rejected`。
- `labelSource` 不是 `codex_manual`。
- 执行合并时 `reviewStatus` 不是 `approved`。

## 7. 开放标签策略

开放标注的目标是让模型充分描述图像，再由人工复核决定哪些标签值得进入正式 catalog。

| 层级 | 用途 | 是否进入 catalog | 是否参与 Worker 匹配 |
| --- | --- | --- | --- |
| `tags` | 模型生成的开放视觉标签 | 审核通过后进入 | 是，仍沿用现有 `tags` 匹配 |
| `attributes` | 长度、形状、覆盖区域、风格、情绪等多维信息 | 第一版不进入 | 否 |
| `reviewStatus` | 机器可读审核状态 | 不进入 | 否 |
| `evidence` | 解释视觉证据 | 审核通过后可进入 | 否 |

任务包会保留 `referenceTags/currentTags`，但它们只作为参考，不限制模型输出。模型不应为了贴合旧标签而牺牲视觉准确性。

## 8. Smoke 流程

smoke 默认选择跨组 5 个样本，用来验证截图、任务包、开放 JSONL、分批报告和合并约束。

推荐样本：

| optionId | 覆盖点 |
| --- | --- |
| `FacialHair:1` | 胡子 / 小胡子 |
| `Headwear:10` | 帽子 / cap |
| `Glasses:1` | 眼镜 / 圆形或框型 |
| `MainHair:48` | 发型 / 多维属性 |
| `Expression:31` | 表情 / 情绪标签 |

流程：

```bash
npm run semantic:codex:tasks -- --smoke
# Codex 只读取 .cache/avatar-semantic/codex/tasks/smoke-001.json 和该批图片，
# 然后写入 .cache/avatar-semantic/codex/labels/smoke-001.jsonl
npm run semantic:codex:report
npm run semantic:codex:merge -- --input .cache/avatar-semantic/codex/labels/smoke-001.jsonl --check-only
```

注意：默认 `reviewStatus=pending` 会让 merge check 失败，这是预期行为。只有人工把需要合并的条目改为 `approved` 后，才允许真实合并。

## 9. 全量识别流程

full 默认覆盖 175 个 `kind=feature` 选项，包括 6 个 none / 不可见项。颜色类选项继续使用 config 色值生成标签，不交给 Codex 猜测。

分批规则：

| 项目 | 默认值 |
| --- | --- |
| 范围 | `kind=feature` |
| 数量 | 175 |
| 批大小 | 10 |
| 图片输入 | 三栏对比图 |
| 输出 | 每批独立 JSONL，例如 `labels/features-001.jsonl` |
| 报告 | 每批独立报告，例如 `reports/features-001.md` |
| 总览 | `reports/index.md` 只做索引、统计和跳转 |
| 恢复方式 | 已存在且校验通过的批次不重复标注 |

流程：

```bash
npm run semantic:codex:tasks -- --all-features --batch-size 10
```

Codex 按批处理：

1. 读取一个 batch 任务 JSON。
2. 查看该 batch 的三栏对比图。
3. 只写该 batch 的 JSONL，例如 `labels/features-001.jsonl`。
4. 不读取其他 batch report、总索引或历史长上下文。
5. 每批完成后运行 `npm run semantic:codex:report` 更新该批报告和总索引。

合并与验证：

```bash
npm run semantic:codex:report
npm run semantic:codex:merge -- --input .cache/avatar-semantic/codex/labels/features-001.jsonl --check-only
# 人工把通过项 reviewStatus 改为 approved 后：
npm run semantic:codex:merge -- --input .cache/avatar-semantic/codex/labels/features-001.jsonl
npm run semantic:check
npm run test:static
npm run test:worker
git diff --check
```

full 验收：

- 175 个 feature option 都有 v2 JSONL 结果。
- 每批都有独立 Markdown 报告。
- `reports/index.md` 能展示 batch 进度、分组统计、`reviewStatus` 统计和跳转链接。
- 未审核 `pending` 或拒绝 `rejected` 的结果不能合并进 catalog。
- 颜色类 option 保持 deterministic/config 标签来源。
- `assets/avatar_semantic_catalog.json` 仍通过 `npm run semantic:check`。

## 10. 与 Actions 结果对比

Codex 本地标注通道和 Actions / Cloudflare 通道应互为复核，而不是互相覆盖。

建议对比维度：

| 维度 | 说明 |
| --- | --- |
| tag overlap | 两边 `tags` 的交集和差异 |
| attributes coverage | Codex 是否提供了更细的视觉维度 |
| confidence delta | 置信度差异过大的 option |
| review mismatch | 一边 `needsReview=true`、另一边为 false |
| evidence quality | 证据是否能解释图像差异 |
| runtime impact | 差异是否影响 `selectionIntent` 匹配结果 |

对比报告默认写入 `.cache/avatar-semantic/codex/compare-report.md`，不提交。只有当对比结果形成稳定决策时，才把结论写入 `docs/agent-steps/03.1-semantic-catalog-review.md` 或后续 roadmap。

## 11. 项目内 skill 设计

后续可新增：

```text
.codex/skills/avatar-semantic-labeler/SKILL.md
```

skill 触发场景：

- 用户要求用 Codex / Codespaces 标注 Duolingo avatar semantic catalog。
- 用户要求复核三栏对比图并输出 semantic labels。
- 用户要求生成或修正某一批 `labels/*.jsonl`。

skill 必须规定：

- 只读取当前 batch 任务 JSON、当前 batch 图片、当前 batch labels/report。
- `tags` 是开放标签，可以自由生成。
- 必须输出 `attributes` 对象。
- 每个 option 必须给 `evidence`。
- 默认 `reviewStatus=pending`，不得自行写 `approved`。
- 看不清、差异过小、标签冲突时必须设置 `needsReview: true`。
- 不直接编辑 `assets/avatar_semantic_catalog.json`；只输出 JSONL，由脚本在审核后合并。

skill 不负责：

- 枚举 Rive option。
- 启动浏览器或截图。
- 写入 catalog。
- 创建 GitHub 私有仓库。

## 13. 实现验收

实现完成后，至少验证脚本入口、JSONL 校验、报告生成、catalog 校验和文档格式：

```bash
python3 -m py_compile scripts/semantic_catalog.py scripts/semantic_codex.py
python3 tests/test_semantic_codex.py
npm run semantic:codex:tasks -- --help
npm run semantic:codex:merge -- --help
npm run semantic:codex:report -- --help
npm run semantic:check
git diff --check
```

验收标准：

- npm scripts 暴露 `tasks`、`merge`、`compare`、`report` 四个入口。
- `tasks` 在可用浏览器环境中生成任务 JSON、manifest、三栏对比图和每批 labels 路径。
- `merge --check-only` 能拒绝 schema、optionId、group、attributes、confidence、reviewStatus、labelSource 等错误。
- `merge` 只接受 `reviewStatus=approved` 的结果。
- `report` 能输出分批报告和总索引。
- 未审核开放标签不会进入正式 catalog。
