# 03.2 Codex 本地语义标注

## 1. 背景与结论

03.1 已经把运行时生成链路改为 semantic catalog 驱动：前端提交可用选项，Worker 让模型输出目标特征，再由 Worker 匹配合法 `state/value`。这个方向可以避免模型直接猜 Rive 数字值，但 catalog 本身仍需要更可靠的视觉语义标签。

可以使用 Codex 在 Codespaces 内做基本元素的语义识别标注。它适合作为一个半自动、本地可复核的标注通道，用来和 GitHub Actions / Cloudflare 视觉模型标注互相对比。

关键结论：

- Codex 负责看图、识别语义、按固定 JSONL 输出标注结果。
- 脚本仍负责机械任务：枚举 option、渲染三栏对比图、生成任务包、校验 JSONL、合并 catalog、生成复核报告。
- 这个通道不接入用户 Generate，不接入部署流程，不替代 03.1 的运行时设计。
- 本文档只定义后续实现方案；当前步骤不实现脚本、不创建 skill、不生成截图、不跑 full 标注、不更新 `assets/avatar_semantic_catalog.json`。

## 2. 适用边界

| 项目 | Codex 本地标注 | Actions / Cloudflare 视觉模型 |
| --- | --- | --- |
| 运行位置 | Codespaces 当前工作区 | GitHub Actions |
| 调用方式 | 人工让 Codex 按任务包分批看图 | workflow_dispatch 手动触发 |
| 模型职责 | 识别三栏对比图，输出 JSONL | 通过 Cloudflare REST 视觉模型输出结构化结果 |
| 结果落地 | 本地 JSONL，经脚本合并后提交 | Draft PR 或 artifact |
| 优点 | 易复核、可解释、能快速人工纠偏 | 可重复、批量化、无需交互 |
| 风险 | 交互式，批量耗时；依赖 Codex 当前会话视觉能力 | 受模型和 API 质量影响；成本和密钥管理更重 |

不应把 Codex skill 设计成“自动枚举和持久化所有结果”的唯一执行引擎。skill 只提供标注工作流、质量标准和输出格式；确定性操作必须放在项目脚本里。

## 3. 整体流程

```mermaid
flowchart TD
  C[avatar_builder_config.json] --> E[枚举 feature options]
  E --> B[渲染 baseline PNG]
  E --> O[渲染 option PNG]
  B --> D[生成 diff PNG]
  O --> D
  D --> T[三栏对比图 baseline | option | diff]
  T --> P[Codex 任务包 JSON]
  P --> S[Codex skill 分批识别]
  S --> L[labels.jsonl]
  L --> V[脚本校验 schema / optionId / 受控 tags]
  V --> M[合并到 avatar_semantic_catalog.json]
  M --> R[复核报告与对比报告]
```

三栏对比图是默认输入，原因是单张 option 图容易漏掉细节变化，尤其是表情、皱纹、耳饰、鼻环、眼镜边框等小元素。

```
+----------------+----------------+----------------+
| baseline       | option         | diff           |
| 默认头像截图   | 当前选项截图   | 像素差异高亮   |
+----------------+----------------+----------------+
```

## 4. Codespaces 浏览器准备

渲染 Rive 头像需要真实浏览器运行 Rive/WASM、应用 state、从 `riveCanvas` 导出 PNG。Codex 可以识别图片，但图片仍必须先由浏览器渲染得到。

当前 Codespaces 不保证预装 Chrome/Chromium。后续实现默认采用 Playwright 下载的 Chromium 缓存，但不把 Playwright 固定加入 `package.json`，避免把一次性浏览器下载变成项目运行时依赖。

推荐准备命令：

```bash
npx playwright install --with-deps chromium
```

脚本查找浏览器的顺序：

| 顺序 | 来源 | 说明 |
| --- | --- | --- |
| 1 | `CHROME_EXEC` | 用户显式指定浏览器路径，优先级最高 |
| 2 | 系统命令 | `google-chrome`、`google-chrome-stable`、`chromium`、`chromium-browser` |
| 3 | Playwright Chromium 缓存 | 从 `~/.cache/ms-playwright/` 中查找可执行文件 |

如果三者都找不到，任务生成应失败，并提示先执行 Playwright 安装命令或设置 `CHROME_EXEC`。

## 6. JSONL 输出格式

Codex 标注结果采用 JSONL，每行对应一个 option。

```json
{
  "schemaVersion": 1,
  "optionId": "FacialHair:1",
  "group": "facial_hair",
  "tags": ["mustache", "short"],
  "extraTags": ["classic_mustache"],
  "confidence": 0.86,
  "needsReview": false,
  "evidence": "The option adds a short dark mustache above the mouth.",
  "labelSource": "codex_manual",
  "imagePath": ".cache/avatar-semantic/codex/images/FacialHair_1.compare.png"
}
```

字段规则：

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| `schemaVersion` | 是 | 固定为 `1` |
| `optionId` | 是 | 必须存在于当前 `avatar_builder_config.json` 枚举结果 |
| `group` | 是 | 必须等于该 option 的 semantic group |
| `tags` | 是 | 只能使用受控词表内的标签，会进入 Worker 自动匹配 |
| `extraTags` | 是 | Codex 补充语义，只用于人工复核和后续词表演进 |
| `confidence` | 是 | `0..1`，低于阈值时合并为 `needsReview: true` |
| `needsReview` | 是 | Codex 主观不确定、图像差异过小、标签冲突时为 `true` |
| `evidence` | 是 | 简短视觉证据，说明为什么选择这些标签 |
| `labelSource` | 是 | 固定为 `codex_manual` |
| `imagePath` | 是 | 指向本次识别使用的三栏对比图 |

合并脚本必须拒绝以下结果：

- JSON 解析失败或缺少必填字段。
- `optionId` 不存在、重复或不在当前任务包中。
- `group` 与 catalog 枚举结果不一致。
- `tags` 包含受控词表之外的值。
- `confidence` 不是 `0..1` 数字。
- `labelSource` 不是 `codex_manual`。

## 7. 标签词表策略

`tags` 和 `extraTags` 必须分开：

- `tags`：受控标签，用于 Worker 运行时匹配，必须稳定、少量、可验证。
- `extraTags`：开放描述，只用于人工复核和后续词表演进，不参与 Worker 匹配。

示例：

| group | 受控 tags 示例 | extraTags 示例 |
| --- | --- | --- |
| `facial_hair` | `mustache`, `goatee`, `full_beard`, `sideburns`, `none`, `unclear` | `toothbrush_mustache`, `rounded_beard` |
| `headwear` | `hat`, `bowler_like`, `brimmed_hat`, `cap`, `soft_hat`, `none`, `unclear` | `beanie_like`, `flat_cap_like` |
| `main_hair` | `short_hair`, `medium_hair`, `long_hair`, `receding_hair`, `neat_hair`, `unclear` | `side_part`, `spiky_top` |
| `expression` | `serious`, `stern`, `calm`, `smile`, `friendly`, `surprised`, `playful`, `neutral`, `unclear` | `raised_eyebrows`, `sleepy_eyes` |
| `glasses` | `round_glasses`, `square_glasses`, `bold_glasses`, `none`, `unclear` | `thin_frame`, `large_lenses` |

后续如果某个 `extraTags` 在多次复核中稳定出现，再单独扩大受控词表，并同步更新 Worker 测试。

## 8. 测试识别流程

smoke 默认选择跨组 5 个样本，用来验证截图、任务包、Codex 输出、合并校验和复核报告。

推荐样本：

| optionId | 覆盖点 |
| --- | --- |
| `FacialHair:1` | 胡子 / 小胡子 |
| `Headwear:10` | 帽子 / bowler-like |
| `Glasses:1` | 眼镜 / 圆形或框型 |
| `MainHair:48` | 发型 / 短发或后退发际线 |
| `Expression:31` | 表情 / 严肃或冷静 |

流程：

1. 准备 Chromium：

```bash
npx playwright install --with-deps chromium
```

2. 生成 smoke 任务包：

```bash
npm run semantic:codex:tasks -- --smoke
```

3. 使用项目内 skill 让 Codex 逐图识别，并只输出 JSONL。

4. 合并前校验：

```bash
npm run semantic:codex:merge -- --input .cache/avatar-semantic/codex/labels.jsonl --check-only
```

5. smoke 通过后再真实合并：

```bash
npm run semantic:codex:merge -- --input .cache/avatar-semantic/codex/labels.jsonl
npm run semantic:check
git diff --check
```

smoke 验收：

- 5 个样本都生成三栏对比图。
- Codex 输出 5 行 JSONL，字段完整。
- `tags` 全部来自受控词表。
- 合并报告没有 schema、optionId、group 或标签错误。
- 低置信度或图像差异不明显的样本被标记为 `needsReview: true`。

## 9. 全量识别流程

full 默认覆盖 175 个 `kind=feature` 选项，包括 6 个 none / 不可见项。颜色类选项继续使用 config 色值生成标签，不交给 Codex 猜测。

分批规则：

| 项目 | 默认值 |
| --- | --- |
| 范围 | `kind=feature` |
| 数量 | 175 |
| 批大小 | 10 |
| 图片输入 | 三栏对比图 |
| 输出 | 追加到同一个 `labels.jsonl` |
| 恢复方式 | 已存在且校验通过的 `optionId` 不重复标注 |

流程：

```bash
npm run semantic:codex:tasks -- --all-features --batch-size 10
```

Codex 按批处理：

1. 读取一个 batch 任务 JSON。
2. 查看该 batch 的三栏对比图。
3. 每个 option 输出一行 JSONL。
4. 完成一批后立即运行 merge check。
5. 失败时只修正该批 JSONL，不重新处理已通过批次。

合并与验证：

```bash
npm run semantic:codex:merge -- --input .cache/avatar-semantic/codex/labels.jsonl
npm run semantic:check
npm run test:static
npm run test:worker
git diff --check
```

full 验收：

- 175 个 feature option 都有 Codex JSONL 结果。
- 颜色类 option 保持 deterministic/config 标签来源。
- `needsReview` 项进入 `docs/agent-steps/03.1-semantic-catalog-review.md`。
- `assets/avatar_semantic_catalog.json` 仍通过 `npm run semantic:check`。
- Worker 测试中的人物名样例仍能通过 semantic tags 匹配可见改动。

## 10. 与 Actions 结果对比

Codex 本地标注通道和 Actions / Cloudflare 通道应互为复核，而不是互相覆盖。

建议对比维度：

| 维度 | 说明 |
| --- | --- |
| tag overlap | 两边 `tags` 的交集和差异 |
| confidence delta | 置信度差异过大的 option |
| review mismatch | 一边 `needsReview=true`、另一边为 false |
| evidence quality | 证据是否能解释图像差异 |
| runtime impact | 差异是否影响 `selectionIntent` 匹配结果 |

对比报告默认写入 `.cache/avatar-semantic/codex/compare-report.md`，不提交。只有当对比结果形成稳定决策时，才把结论写入 `docs/agent-steps/03.1-semantic-catalog-review.md` 或后续 roadmap。

## 11. 项目内 skill 设计

后续可新增：

```text
.codex/skills/avatar-semantic-labeler/SKILL.md
```

skill 触发场景：

- 用户要求用 Codex / Codespaces 标注 Duolingo avatar semantic catalog。
- 用户要求复核三栏对比图并输出 semantic labels。
- 用户要求生成或修正 `labels.jsonl`。

skill 必须规定：

- 只使用任务包给出的 `allowedTags` 输出 `tags`。
- 可自由补充 `extraTags`，但不得把 `extraTags` 当作运行时匹配标签。
- 每个 option 必须给 `evidence`。
- 看不清、差异过小、标签冲突时必须设置 `needsReview: true`。
- 不直接编辑 `assets/avatar_semantic_catalog.json`；只输出 JSONL，由脚本合并。

skill 不负责：

- 枚举 Rive option。
- 启动浏览器或截图。
- 写入 catalog。
- 创建 GitHub 私有仓库。
